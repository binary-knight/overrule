# Overrule reference

The long-form description of every feature and its limits. The [README](../README.md) is the short version; the [security policy](../SECURITY.md) states the trust model.

A private web workspace where models hold a meeting: they open independently, then argue on a shared floor with objections, concessions, and a vote on the final deliverable. Runs locally, with no runtime dependencies beyond Node.js 22 or newer.

## Start

```sh
cd overrule
npm start
```

Open **http://localhost:4310**. Choose **Try a scripted demo** to explore without using any provider credits. Set `PORT=4311` if the default port is busy. The server binds to `0.0.0.0` for LAN access. Set `OVERRULE_HOST=127.0.0.1` for access from this machine only.

The interface follows your system's light or dark preference. The moon or sun button in the top bar overrides it for this browser; the choice is stored in the browser's local storage.

### Restart from your terminal

Run this on the host machine, from any directory:

```sh
./restart.sh
```

Or run `npm restart` inside this project. The script stops only this checkout's Node server on the selected port, starts it in the background, and checks for an HTTP 200 response. It also starts the server if it was stopped. You can close your terminal afterward. A process belonging to another app is left alone, and concurrent restarts are refused.

Output is appended to `data/server.log`; the new PID is recorded in `data/server.pid`. To follow the output, run `tail -f data/server.log`. It uses the same `PORT`, `OVERRULE_HOST`, and `OVERRULE_DATA_DIR` environment variables as the server; set them on each invocation if using nondefault settings. `NODE_BIN` can select a Node executable. This helper requires Linux, Python 3, Node.js 22+, and `lsof`, all installed on this machine.

Restarting interrupts active meetings and invalidates LAN sessions. This version generates a new pairing code on every start; retrieve it from **LAN access** on localhost or the private `data/lan.json` file.

## Access from your local network

On the host machine, open **http://localhost:4310 → LAN access**. It shows the machine's detected IPv4 LAN URLs and a pairing code. On another device on the same network, open one of those URLs and enter the code. A typical address looks like **http://192.168.1.20:4310**; DHCP may change it.

The pairing code is new on every server start and can be rotated from the LAN access dialog, which signs out every paired device; it is also saved in the owner-readable `data/lan.json` file for headless setup. Paired devices can use all configured providers and read the shared history. Sessions last at most 24 hours and are invalidated by a server restart. Only a browser connecting through localhost can retrieve the pairing code from the app. Wrong-code attempts are rate limited. Restart the app if its network addresses change. If another device cannot connect, check that both devices are on the same LAN and that the host firewall permits inbound TCP 4310 from that LAN; the app does not modify the firewall.

LAN traffic uses HTTP. Use it on your trusted network; an untrusted network requires HTTPS or a trusted encrypted tunnel. No public Internet deployment or port forwarding is configured.

### The pairing code over SSH

`npm run pair` (or `node scripts/pairing-code.mjs`) prints the running server's pairing code and its addresses, grouped into Tailscale, this network, and virtual bridges other devices cannot reach, with a ready command line for `bin/overrule.mjs`. It asks the server over localhost, the one route the code is answered on, so it works from an SSH session without the host's screen. `--rotate` issues a new code and signs out every paired device; `--json` prints one object. When the server is not running it shows the last saved code with a warning, because starting the server makes a new one: start it first, then read the code. It honours `PORT` and `OVERRULE_DATA_DIR`.

### Access over Tailscale

If the host runs Tailscale, its tailnet address (100.64.0.0/10) is one of the interfaces the server detects, so it already appears in the LAN access dialog, the server log and `npm run pair`, and the same pairing applies: open `http://<tailnet address>:4310` from any device signed into your tailnet and enter the code. Tailscale encrypts the traffic between devices, so the plain-HTTP caution above does not apply on that path. The host firewall still has to admit TCP 4310 on the `tailscale0` interface (`sudo ufw allow in on tailscale0 to any port 4310` under ufw); the app does not change the firewall. The MagicDNS name is not accepted as a Host header; use the address.

## Connect your models

The default council contains Codex and Claude Code. Install current versions of their official CLIs if needed, then sign in **in your own terminal**:

```sh
codex login
claude auth login
```

Connection cards check each CLI's own sign-in status (`codex login status` and `claude auth status`) when the app starts and whenever you use **Check sign-in**. A CLI that reports it is signed out blocks a discussion before any call is spent; the app probes once more first in case you signed in since the last check. Older CLIs that cannot report status show as unchecked and are not blocked. Live errors appear in the discussion. CLI connections use each tool's active authentication, including its normal environment-variable precedence. The app never reads or imports their token files. Leave the model field blank for the tool's default, or enter an explicit model ID. Codex user configuration is ignored for isolated execution; a model selected in your ordinary Codex configuration is therefore not inherited.

Add further connections from **Connections → Add connection**:

| Connection | Authentication | Protocol |
| --- | --- | --- |
| Codex local | Official CLI's active sign-in | `codex exec --json` |
| Claude Code local | Official CLI's active sign-in | `claude --print --output-format json` |
| OpenAI API | Saved key or `OPENAI_API_KEY` | Responses API |
| Anthropic API | Saved key or `ANTHROPIC_API_KEY` | Messages API |
| Gemini API | Saved key or `GEMINI_API_KEY` | Google's OpenAI compatibility endpoint |
| Grok API | Saved key or `XAI_API_KEY` | Chat Completions API |
| Hugging Face Inference Providers | Saved token or `HF_TOKEN` | OpenAI-compatible chat completions via the HF router |
| OpenAI-compatible | Optional saved key | Custom `/chat/completions` endpoint |

### Choosing models

Every connection names one model, and you can hold as many connections per provider as you like, so a council can seat GPT-5.6 Sol, GPT-6 Astra, Claude Opus 5, Claude Fable 5.1, and a local model side by side. Use **Add another model** on a connection card to add a sibling with a different model. Leaving a CLI connection's model blank uses the tool's default. A meeting seats 2–8 members; every member is a separate voice, and turns run one at a time, so eight members is a long meeting.

### Model suggestions

The model field suggests the models the provider itself lists, so a new release appears without an update to this app. The server asks, because it holds the keys; the browser and the command line receive only the list.

| Connection | Where the list comes from | Key |
| --- | --- | --- |
| Codex | `codex debug models`, in the order the CLI gives | The CLI's own sign-in |
| Claude Code | The aliases `fable`, `opus`, `sonnet`, `haiku`, which the CLI resolves to the newest model of each family, plus Anthropic's `GET /v1/models` | `ANTHROPIC_API_KEY` on the server, else the first saved Anthropic API connection's key; without one, only the aliases |
| OpenAI, Grok | `GET /v1/models` | Required |
| Anthropic | `GET /v1/models`, every page | Required |
| Gemini | `GET /v1beta/models`, every page, which says which models generate content; the `models/` prefix is dropped because the compatibility endpoint takes the bare ID | Required, sent in the `x-goog-api-key` header, never in the URL |
| Hugging Face | The router's `GET /v1/models`, which names the inference providers serving each model | Optional |
| OpenAI-compatible | `GET <base URL>/models` (Ollama, LM Studio, vLLM, llama.cpp) | Optional |

Only models a member can hold a conversation with are offered: embedding and ranking, speech and realtime, image and video, moderation, and document-retrieval models are hidden, judged from the provider's metadata where it gives any (Gemini's supported methods, Hugging Face's output modalities) and otherwise from the model ID. OpenAI's legacy completion models and models that need tools members do not have (search-preview, computer-use, deep-research) are hidden too. The name rules are a heuristic, so the status line says how many were hidden and `overrule models <type> --all` lists them with the reason. Lists are sorted newest first: by the provider's creation date where it gives one, otherwise by the version in the name.

The list is fetched when the form opens, when the type changes, when a key is pasted, and when a compatible server's base URL is entered (once the field is left, never at a half-typed address). The status line under the field says how many models came from where, with which key, and how long ago; **Refresh list** asks again. A key typed into the form is used before it is saved. Otherwise an existing connection's saved key is used, but only while its type and, for a compatible server, its base URL are unchanged: a saved key is never sent to an address it was not saved for, the same rule saving follows. The server's environment key comes last. Changing the type clears a typed key, so it never reaches another provider. Providers that list only for a key (OpenAI, Anthropic, Gemini, Grok) are not asked without one.

Lists are cached for ten minutes per provider, address, and key, in memory and in `data/models.json`, so the last list survives a restart and an unreachable provider. Keys are never written there; a keyed hash tells one key's list from another's, because different keys can see different models. A damaged or unreadable `models.json` costs only the cached lists: the server starts, logs one line saying so, fetches lists again, and rewrites the file.

**When a provider fails.** Asking for a list gives up after ten seconds, and the deadline covers the whole answer: a provider that never answers, answers slowly, or sends its headers and then goes quiet is given up on at the deadline, and the connection to it is closed. The status line counts the seconds while it waits and says when it will give up. A failure is stated in the app's own words with what to check: the provider could not be reached or did not answer in time (shown as **⚠ Can't reach**, with, for a compatible server, the address to check and, for one on this machine, a reminder such as `ollama serve`), the key was rejected, rate limited, no model list at this endpoint, a redirect refused, a list over 8 MB, or an answer that is not a model list. The provider's response body is never shown, because providers echo part of a rejected key. If an earlier list exists it stays on offer, marked with its age, and the line says the provider cannot be reached now. A failure is remembered for thirty seconds, so typing, reopening the form, or another device asking does not wait on a dead provider again; the line says when it was tried, and **Refresh list** asks at once. While one request to a provider is under way for a key, everyone else asking for that list shares its answer rather than sending another. An empty list is an answer, not an error. A list with broken entries keeps the entries that can be read and says how many were skipped; a list longer than 2,000 models, or one that says there is more without saying how to ask for it, is marked as incomplete. Saving a connection waits at most three seconds for the list it checks the model against; past that the model is saved as not yet checked, and the request carries on in the background and fills the cache.

**Keys as pasted.** Spaces and line breaks around a key, as copying often adds, are removed before it is used or saved; a server environment key is trimmed the same way. A key with anything but visible ASCII inside it cannot travel in an HTTP header, so it is refused with that reason, never repeated.

Any ID can be typed, because new releases, Hugging Face's `:provider` suffixes, and local tags all exist. An ID not on the list shows a warning under the field while it is typed, and saving it succeeds with the warning repeated, in one of three forms: the ID is not among the models the provider listed; the provider lists it as a model that is not for conversation; or it was not checked, because no list could be read, or because only Claude Code's aliases are known. Ollama's `name` and `name:latest` count as the same model, and a Hugging Face ID is compared without its suffix. Editing a connection checks again only when its type, model, address, or key changed.

Over HTTP, `POST /api/models` with `{ "type", "connectionId"?, "baseUrl"?, "apiKey"?, "refresh"? }` returns `{ models: [{ id, label?, created?, context?, description? }], hidden: [{ id, reason }], source, keySource, fetchedAt, cached, stale, error }`; it needs the page token, like every change, because it can carry a key. Saving a connection (`POST /api/providers`, `PUT /api/providers/<id>`) returns `modelCheck: { status, detail }` with status `listed`, `unlisted`, `not-for-conversation`, or `unchecked`. From the command line, `overrule models <type or connection>` prints the same list and `overrule connections add|edit` prints the same warning.

### Testing a connection

**Test connection** in the connection form tries what the form holds, before anything is saved: the same validation as saving, the same key rules as the model list (a typed key, else the saved key while the type and address are unchanged, else the server's environment key; **Remove saved key** ticked means no saved key), and one short message ("Reply with the word OK") through exactly the path a meeting uses. API providers bill it as a few tokens; it allows at most 256 output tokens and 30 seconds, or two minutes for a compatible server on this machine, whose first request may load a model into memory. A CLI connection has its sign-in checked afresh, then the CLI runs once in an empty temporary directory with tools off, as a member with no workspace does; that counts against its plan and is allowed two minutes. While it runs, the result counts the seconds and says when it will give up, and the button becomes **Cancel test**. Closing the form or changing it also cancels a test in progress, and any change to the form clears the result, so a result always describes what **Save** would store. Nothing is written: not the key, not the model.

The result is a checklist. For an API connection: whether the provider was reached, whether the key was accepted, and whether the model answered, with its reply and how long it took. A failure names the part that failed: the key rejected (401) or refused for this model (403); the model unknown to the provider (404, or for a compatible server a base URL that is not an OpenAI-compatible API); the request refused (400); no credit or quota left; rate limited, which means the key works; an error at the provider (5xx); no answer in time; unreachable; a redirect refused; a reply in a format this connection type does not read; or no key to test with. The provider's short error code (such as `invalid_api_key`, `model_not_found`, or `insufficient_quota`) is shown beside the HTTP status; its error message never is, because providers echo part of a rejected key. A reasoning model that spends the whole small allowance thinking and writes nothing has still accepted the key and the model, so that counts as a pass and says so. An empty reply passes with a warning, because a meeting turn needs text. For a CLI connection the checklist says whether the CLI is installed and signed in, and then whether the model answered or what the CLI said when it did not.

Over HTTP, `POST /api/providers/test` takes the body that saving takes, plus `connectionId` to use a saved connection's key, and returns `{ ok, checks: [{ state: "ok" | "warn" | "fail", text }], type, model, target, keySource, ms, reply?, usage? }`; a form that could not be saved comes back as a failed test rather than an error. From the command line, `overrule connections test` takes what `connections add` takes, or a connection's name whose saved values the other options override, prints the same checklist, and exits 0 when the connection works and 1 when it does not.

Open and local models use the **OpenAI-compatible** type with a preset: Ollama, LM Studio, vLLM, and llama.cpp servers on this machine, or **Hugging Face Inference Providers** (a separate type) for hosted open-weight models through `https://router.huggingface.co/v1` with a Hugging Face token; the model ID there is the Hub name, optionally with a `:provider` or `:cheapest` suffix. Gemini and Grok use their API types.

For compatible services, supply a **base URL** such as `https://provider.example/v1` or `http://localhost:11434/v1`, not the full chat-completions URL. Remote endpoints require HTTPS. Redirects are rejected to prevent forwarding credentials. Other providers can be used when they implement this protocol; arbitrary OAuth flows and provider-specific noncompatible APIs require another adapter. Enter a model available to your account. Provider keys are never sent back to the browser after saving.

Subscription access is not a general API credential. This personal app invokes unmodified local tools and leaves sign-in with the vendor. Native API connections use separate provider API billing. Gemini and Grok subscription sign-in are not implemented. CLI account eligibility and limits remain controlled by the provider. Do not turn this into a shared subscription proxy.

### Saved councils

A saved council is a named set of seats with whichever meeting settings you choose to keep, stored on the host in `data/councils.json` so the browser, paired devices, and the command line share it, across restarts. Set up councils for particular purposes (a full council for architecture questions, two seats for quick ones) and seat one in a step instead of ticking connections and setting options each time.

A council always keeps its seats, 2 to 8 saved connections. Besides the seats it keeps any of five groups, chosen with tick boxes when you save it: the **drafter** (and whether it drafts as a neutral drafter), the **meeting length** in cycles, the **revisions** allowed after objections, **research** (internet research and deep research), and **limits** (the session's call and time limits, output tokens per call, and time per call). Picking a council seats exactly its seats and applies only the groups it kept; everything it did not keep stays as the form has it, so a council that keeps only seats and cycles leaves research and limits to each meeting. A kept automatic call limit stays automatic, so it follows the council's seats and cycles.

In **Choose your council**, the **Saved council** menu applies a council, and the line beneath it says what the council keeps and, once you change anything it keeps, what you changed; the meeting records the council it started from and those changes, and shows them under its title. **Save as council…** saves the seats and settings now in the form. With a council picked, the dialog starts from that council: its name, its purpose, and the groups it keeps; saving under the same name updates it, a different name saves a new council beside it unless you tick **Rename** instead, and a name another council already has replaces that council after the dialog says so. **Save council…** in a meeting's view saves that meeting's seats and settings as it last ran, after any resume or reconvene; members whose connections have since been deleted are left out, and said to be. **Delete council** removes the council only: its connections stay saved, and meetings it started keep its name on their record.

Deleting a connection takes it out of every council that seats it, and the confirmation says which councils changed and how many seats each has left. A council whose drafter was that connection no longer names a drafter, and a neutral drafter with fewer than three seats left stops being neutral. A council left with one seat is marked **needs seats**: picking it seats what is left, and a meeting from the command line says what to do. Up to 50 councils can be saved.

Leaving a connection unticked for a meeting never deletes it: the connection stays under Connections, ready to be ticked again with its key and model as they were.

Over HTTP: `GET /api/councils` lists councils, each with `seatNames` and `incomplete`; `POST /api/councils` with `{ name, purpose, seats, settings, replace }` saves one, answering 409 with `code: "exists"` when the name is taken and `replace` is not set; `PUT /api/councils/<id>` changes one, including its name; `DELETE /api/councils/<id>` removes one. `settings` holds only the kept groups: `drafter: { drafterId, neutralDrafter }`, `cycles`, `revisions`, `research: { research, deepResearch }`, `limits: { maxCalls (null for automatic), maxDurationSeconds, maxTokens, timeoutSeconds }`. A meeting started with `council: { id, changed }` records `council: { id, name, changed }`, the name taken from the saved council. Deleting a connection answers with `councils: [{ id, name, seatsLeft, notes }]`.

## How a meeting runs

1. Select 2–8 members, or pick a saved council, and give each an optional perspective (builder, critic, domain expert, etc.). Multiple models from one provider are supported. Choose the meeting length in cycles (a cycle is one turn per member) and which member drafts the deliverable.
2. **Opening.** Every member writes a position without seeing the others: a proposed approach, key assumptions, the principal risk, and acceptance criteria. Openings are revealed together so no member anchors the rest.
3. **Floor.** Members speak one at a time, each reading the whole thread. A turn must quote the exact claim it answers before rebutting or conceding. Objections carry the claim they touch and a concrete condition that would resolve them, get a stable id, and stay open until the member who raised them assesses that condition. A member who moves from disagree to agree must cite the entry and quote that changed its mind; an uncited change is re-asked once and otherwise recorded as disagree. Each turn ends with a stance (agree, disagree, need-info) and nominates the next speaker. Each active member gets one opportunity per cycle. Among members who have not yet had their turn, priority goes to the target of an unanswered objection, then the nominee, then the member heard least recently. A failed turn uses that opportunity; an interrupted turn is retried on resume.
4. **You can speak.** Anything you say is delivered at the next turn boundary; the meeting pauses for it and the next member must address it, quoting you. Speaking after a candidate exists invalidates the ballots on it and the candidate is redrawn.
5. **Closing.** The floor closes by consensus (every active member has a successful agree turn in the current session, with no objection open, checked at the end of each cycle; a failed latest turn cannot count as agreement), on budget when the cycles run out, or as stalled when two full cycles pass with no change in stance or objections. The reason is recorded.
6. **Draft and ratify.** The drafter writes the candidate. Every other member votes independently on that exact text (approve, object with claim and condition, or abstain); ballots are revealed together. If any member objects, the drafter revises and the members vote again, for as many rounds as **Revisions after objections** allows (one by default, up to five for a long build-and-review loop; an implementer keeps its checkout between revisions). The final answer is the candidate plus the council record: the close reason, the vote, objections on record verbatim, and any objection still open from the floor.
7. **Reconvene.** A closed meeting can be reopened with a new instruction from the meeting view. The same members carry on with the whole record: the transcript, the objections, the earlier candidate and ballots (shown to them as history), the workspace branch, and the attached documents. The new session requires fresh stances from every active member and gets its own cycle budget, its own draft and ballots, and its own entry in the record; earlier results stay under **Earlier sessions**. In a workspace meeting the next candidate builds on the branch: if you applied the previous one, the new candidate is only the delta; if you discarded it, the branch is recreated. Use this for work that does not fit one sitting, one stage at a time. **Resume** is different: it finishes an interrupted or failed session under the same instruction.

The implementer's per-call time limit, set in the Workspace section, goes up to four hours. The candidate's entire check batch gets a separate deadline of that same duration. Both also obey the session's total active-time limit. Stopping the meeting cancels the checks as well as model calls.

Every prompt carries an **ACCESS THIS TURN** section naming what each member can actually do (a read-only shell, file reading without a shell, or no tools) and that only the drafter writes files, at the draft step, in its own checkout. This stops members spending turns on who holds write access.

A meeting that reaches unanimous agreement from the first floor turn with no cited concession and no objection is labeled **no deliberation occurred**. Treat that result as one answer, not a council decision. Missing responses and abstentions are never counted as agreement. These controls reduce performative agreement; they cannot establish correctness. Independently validate important outputs.

The estimate before Start shows a typical call count and an allowance that includes all configured revisions and one possible re-ask for every floor turn. For example, two members, two cycles, and one revision show 8 typical calls and an allowance of 14. Extra work from owner interjections and retries after an interruption uses the same allowance. Floor turns run one at a time and each reads the whole thread. There are no automatic connection retries or hidden model substitutions. A member whose opening fails does not take part; a member whose floor turn fails is skipped, and dropped after two consecutive failures. The meeting continues while two members remain. A failed drafter marks the meeting failed with the thread intact, and **Resume** continues from the last committed entry, re-running only what was missing; failed and superseded attempts never re-enter the thread.

**Session limits** enforce a maximum number of model-call attempts and a total active duration. The defaults are the calculated call allowance and 60 minutes. A workspace-write or full-access meeting is refused when the session time limit is shorter than the implementer time limit, because a deadline during implementation cancels the draft and discards its checkout; set the session limit to at least the implementer limit, and to twice it when the candidate has checks to run. Calls include failed, cancelled, superseded, and re-asked attempts, but not owner messages or check commands. Independent openings and ballots require room for the whole pending batch before any member starts, so a session can stop just below its call limit. Active time includes preparation, model calls, checks, and cleanup; time spent stopped between resumes is excluded. A total deadline cancels pending calls and checks, saves the record, and shows **Session limit reached**. Cleanup can take additional time after cancellation. Usage displays calls, elapsed active time, and tokens where providers report them; these are not dollar limits.

**Pause** asks the meeting to stop at the next step: the call in flight finishes and is recorded, then the meeting holds with the status *paused*. **Stop** aborts the call in flight instead. Either state resumes the same way.

**Adjust and resume** picks a stopped or paused meeting up under changed settings: workspace access level, network for the implementer and the checks, the check commands, the implementer time limit, the Claude Code sandbox option, meeting length in cycles, revisions after objections, internet and deep research, the time limit for one member's turn, the session limits, and an optional note to the council. The workspace folder, the brief, and the members cannot change, since every member has already read them. What changed is written into the transcript as your own contribution, so the next member answers it, and the prompts state the new access from that turn on. Raising the cycles reopens a floor that closed on its cycle budget, and raises the call allowance to match; a floor closed by consensus or as stalled stays closed. Changing the checks, the network, or the implementer time limit sends a candidate that was already verified back for checking and takes its ballots again. Moving a read-only meeting to a write level asks you to acknowledge uncommitted work, and moving to full access asks for that acknowledgement again. An implementation that was stopped, timed out, or failed keeps its checkout, so the drafter continues from its own partial work. Setting new limits keeps all usage already spent. Restarting cannot reset either limit. After an unclean shutdown, elapsed time since the last active checkpoint is conservatively charged up to the time limit, including downtime; raise the limit if needed to recover. **Reconvene** opens a fresh session with new limits and retains earlier usage in its history. Limits can be set separately on each reconvened session.

Concession citations must identify an earlier completed, non-superseded contribution and quote a passage it actually contains. Matching is case-sensitive, with Unicode and whitespace normalization. Missing sources, future/self references, and fabricated quotes remain visible as rejected citations, but do not count toward concession metrics or justify a disagree-to-agree change. The member gets one re-ask to supply evidence. A matching quote establishes traceability, not correctness.

The result heading distinguishes **Approved**, **Objections remain**, **Checks failed**, and **Verification incomplete**. Floor consensus is displayed separately. Approval requires a completed candidate, approval from every eligible reviewer, no open objections or candidate caveats, and finished verification for workspace changes. Missing ballots and abstentions cannot count as approval; failed configured checks take precedence over model votes. Text-only meetings and workspace meetings with no configured checks explicitly label approval as model agreement without independent automated verification.

The **Evidence and review** panel beside the answer lists the candidate text or reviewed commit, reviewer ballots, unresolved objections and their resolution conditions, check output, and validated concession quotes. Source links open and highlight the corresponding transcript contribution. Markdown exports include the verdict, usage, reviewed commit hashes, and citation links as well.

Workspace candidates have separate capture, **Checks**, and voting steps. If verification is cancelled, times out, or cannot run, voting and Apply wait for it. **Retry candidate checks** reruns the whole check batch from a clean checkout of the same commit without repeating the draft or floor. Checks that finish with a failing exit code are kept as evidence for voters. After a restart, a captured commit is reused; a completed but uncaptured implementation keeps its checkout for recovery. If that checkout was lost, the draft is explicitly superseded and rebuilt. Discarding the branch removes retained checkouts.

Progress uses server-sent events as each contribution begins and completes; individual token streaming is not implemented yet. Runs survive page refreshes. Restarting the server marks unfinished meetings interrupted, which can then be resumed. Your draft brief and council settings are saved in the browser's local storage and restored after a refresh, an expired pairing, or a server restart. Once a meeting is shown, the composer is hidden until you choose **New discussion**; a draft that differs from the shown meeting's prompt is kept. Recent history retains up to 30 completed meetings by default, with active, pinned, and archived ones preserved; **Settings** changes the number, up to what the disk safely holds (see below). The limit is applied when a meeting starts: the meeting starting does not count, and anything past the 30 newest stopped, unpinned meetings is removed exactly as **Delete** removes it (see below): its record, documents and extracted text, patch files, kept checkouts, and candidate branch. The list can briefly hold 31 once that meeting finishes. A meeting that the next start would remove says so in the history, naming an unapplied candidate branch that would go with it. If something of it cannot be removed yet, for example because its candidate branch is checked out in your own tree, nothing of it is removed: it stays in the history with the reason shown, and the next meeting to start tries again. Starting a meeting over HTTP answers once the meetings it pushed out are gone. **Renaming.** **Name…** (or **Rename…**) in the **⋯** menu beside a meeting in the history, or **Name this meeting** (**Rename** once it has a name) in the meeting view, gives it a name of up to 120 characters. The history, the dialogs, the command line, and the Markdown export use the name; the meeting view shows it above the brief. The brief itself never changes, because every member reads it on every turn, resume, and reconvene. An empty name, or **List it by its brief again**, clears it. The name is saved with the meeting in `data/runs.json` and survives restarts; over HTTP it is `PUT /api/runs/<id>/title` with `{ "title" }`, which needs the page token. **Search and filters.** The search box above the history filters the list as you type, after a short pause; an answer to an older query is discarded. A query is words and "quoted phrases", without regard to case, and a meeting matches when every one of them appears somewhere in it: its name, tags and project, full brief, workspace name and origin, document names, member names, id, final answers from every session, or transcript, searched on the host in that order. Each result says where it matched, with an excerpt and the words marked, unless the listing already shows it. The list keeps its shape: pinned meetings and their project groups first, with every group open while filtering, then recent ones. The chips under the box filter by project (one at a time) and tag (each one chosen must be present), and combine with the search; clicking a tag on a meeting toggles that filter. A summary says how many meetings match, how many more matched in the Archive (a link opens it with the same search), and offers **Clear**; Escape in the box clears the search. A long history shows fifty recent meetings at a time, with **Show more**. Over HTTP, `GET /api/runs?q=<query>` lists only matches, archived ones included and flagged, each with `match: { field, snippet, at }`. **Archive.** **Archive** in the **⋯** menu or the meeting view moves a stopped meeting to the **Archive** page in the navigation, which lists archived meetings most recently archived first, with its own search, and offers **Unarchive** and **Delete** for each; opening one shows it with a notice and an **Unarchive** button. An archived meeting keeps everything, including its name, pin, tags, project, documents, and candidate branch; it is hidden from the history list, does not count toward the history limit, and is never removed to make room. It cannot be resumed or reconvened until unarchived, and a meeting in session cannot be archived. Unarchiving returns it to where it belongs: under **Pinned** if pinned, otherwise with the recent meetings in date order, where the limit applies again; if that makes it the next to be removed, the app asks first. Archive state is saved with the meeting in `data/runs.json` and survives restarts; over HTTP, `PUT /api/runs/<id>/archive` archives and `DELETE /api/runs/<id>/archive` unarchives. **Settings.** The gear at the top right opens Settings, saved on the host in `data/settings.json` so they survive restarts and apply to every paired device. **Meeting history** keeps the most recent stopped meetings, not counting pinned or archived ones: any number from 1 up to the room the disk has (30 by default), or **as many as the disk safely holds**, which follows the free space. There is no fixed ceiling; the ceiling is the disk, measured on the host. Meetings may grow into at most half of the space free now, and the disk always keeps a reserve free for everything else: a tenth of its size, and never less than 2 GB. Each meeting is counted at the size of the largest tenth of the meetings already kept (its record, documents, and patch files), and never less than 256 KB, so a history with a few large meetings is estimated cautiously. The room is the meetings the list holds now plus as many more as fit in that allowance: with 80 GB free on a 256 GB disk, that is 40 GB more, about 164,000 meetings at 256 KB. A number above the room is refused. The limit in force is the smaller of the setting and the room, measured afresh before every meeting starts, so a number saved when the disk had space is held to what fits later. When there is no room left the history stops growing: each new meeting replaces the oldest unpinned one, the oldest is marked in the history beforehand, and the dialog says free space is low. It never shrinks to give back space that something else used, and pinned and archived meetings are never touched. If the disk's free space cannot be read, no upper limit applies and nothing is removed to make room. The dialog shows how much space meetings take, the free and total space of the disk, and the arithmetic behind the room under **How the room is worked out**; before a lower limit is saved it says how many meetings would be removed at the next start, and the history marks them, so they can be pinned or archived first. Nothing is removed until a meeting starts. An older settings file's "keep every meeting" is read as "as many as the disk safely holds". Over HTTP, `GET /api/settings` returns `{ historyLimit, effectiveLimit, room, storage, capacity, policy }`, measured afresh; `PUT /api/settings` with `{ "historyLimit": <number or "max"> }` changes it and returns how many meetings the new limit would remove. Listing the history reuses a measurement up to half a minute old. **Pinning.** The pin icon beside a meeting in the history (shown on hover, on the meeting being shown, and always on touch screens) or **Pin** in the meeting view opens one dialog: press Enter to pin, or first give the meeting a project and tags. Pinned meetings are listed under **Pinned** at the top of the history, most recently pinned first: meetings with no project, then one folding group per project in alphabetical order; which groups are folded is remembered by the browser. Pinned meetings do not count toward the 30 and are never removed to make room, however many meetings follow, and a pinned meeting cannot be deleted until it is unpinned. Pinning a meeting in session is allowed; it is protected from the moment it ends. A project name is up to 60 characters; a meeting takes up to 12 tags of up to 32 characters, without commas. Spacing is normalized, a repeated tag is dropped, and a project or tag already in use keeps the spelling it has there, so "billing" joins "Billing" rather than starting a second group; the dialog suggests projects and tags already in use. **Edit pin** in the meeting view, or the pin icon on a pinned meeting, changes the project and tags or unpins it. Unpinning returns the meeting to **Recent meetings** in date order and clears its project and tags; if it has any, or if its place is past the limit so the next meeting would remove it, the app asks first and says which. The pin, its tags, and its project are saved with the meeting in `data/runs.json`, so they survive restarts and show on every paired device. Over HTTP, `PUT /api/runs/<id>/pin` with `{ "project", "tags" }` pins or edits (fields left out keep their values) and `DELETE /api/runs/<id>/pin` unpins; both need the page token. **Deleting a meeting.** A stopped, unpinned meeting can be deleted with **Delete…** in the **⋯** menu beside it in the history (the menu button appears on hover, on the meeting being shown, and always on touch screens), from the Archive page, or with **Delete meeting** in the meeting view. For a meeting in session or a pinned one, the menu item is disabled and says why; the server refuses too, and also refuses while a stopped meeting is still winding down or while an apply, discard, or reconvene on it is in progress. A confirmation dialog reads the meeting first and lists what will go; nothing is removed until you press **Delete permanently**, and **Keep meeting**, the close button, and Escape all cancel. Deleting removes the meeting from `data/runs.json`, its folder under `data/attachments/<meeting id>/` (documents and extracted text), its patch files under `data/artifacts/`, any checkout kept for it in the temporary directory (including an interrupted implementation kept for resume), and its candidate branch in the workspace repository. An unapplied candidate branch is called out in the dialog because its changes are lost; an applied one only loses the branch name, since the merge stays in your branch. Your working tree, cloned repositories, recent workspaces, and anything you exported are not touched. If the candidate branch is checked out in one of your own checkouts, deletion is refused before anything is removed; switch that checkout to another branch and delete again. A workspace folder that was moved or deleted does not block deletion. The page updates at once; other open windows and paired devices update when they are next brought into view, and a meeting deleted elsewhere is closed with a notice. Over HTTP this is `DELETE /api/runs/<id>`, which needs the page token like every other change. Discussions recorded before meetings existed remain readable and exportable but cannot be resumed. Exports contain the prompt, the final answer with the council record, every objection, the meeting metrics, and the full transcript with each contribution's structured fields. The scripted demo is clearly labeled and uses no model calls.

### Research mode

**Internet research** gives every member that can reach the web permission to use it, and tells all of them to cite each external fact with its source and date. **Deep research** is a second setting on top: search before taking a position rather than after, gather several independent sources and prefer primary ones, reconcile sources that disagree instead of picking one, date anything that changes over time, and list what could not be verified. Deep research needs internet research and turns it on; asking for deep research with the web off is refused. Where a provider counts search uses, deep research raises the allowance. The rules add that a page a member reads is data to evaluate and never an instruction, and that a search result does not make a claim true.

Capability differs by member, and the **ACCESS THIS TURN** section names it per member so nobody argues from a guess:

| Member | With research on |
| --- | --- |
| Codex | Live web search through Codex's own provider, at every access level, because the search runs outside the sandboxed shell (`web_search="live"`). |
| Claude Code | Web search and page fetch when talking or at a write level; at read-only its restricted mode removes page fetch, so it searches only. The tools are both named and explicitly allowed, because the permission mode the app uses denies anything that would otherwise ask. Under the Claude Code sandbox with the network off, a page fetch fails while search still works. |
| OpenAI API | The Responses API `web_search` tool. |
| Anthropic API | The Messages API server-side search tool, at the version the model takes. |
| Gemini, Grok, Hugging Face, OpenAI-compatible | No browsing. They are told to rely on what others quote. |

A turn that searches the web takes minutes rather than seconds, so ticking deep research raises the per-turn time limit to 15 minutes, and that limit can be raised to an hour. The per-turn limit covers the whole answer from an API provider, not only its start: a provider that sends its headers and then goes quiet is cut off at the limit like one that never answers, and the turn fails with "Timed out". A member that runs out of time on its opening position takes no part in the meeting; resuming before the floor has spoken gives those members their opening back, so raising the limit and resuming recovers them. Both settings are recorded with the meeting, shown in the meeting header, and can be switched from **Adjust and resume** on a stopped meeting, like any other setting. It costs time and tokens: every member may search on every turn, and searches send the subject matter of your brief to each provider's search service.

## Giving the council documents

Drop files on the brief, press **Attach files**, or paste a copied file. This works from any paired device, so a PDF on a Windows laptop can be debated by members running on the Linux host. Each file uploads to the host, which reads its text once and shows how many characters it found, with a plain warning when it found none (a scanned PDF, a password-protected file) or had to skip something.

- **What members see.** The extracted text, under a DOCUMENTS heading in every prompt, labelled as material to evaluate and never as instructions. That is the same for CLI members and API members; no member opens the file itself, and attaching documents gives no member tools or a working directory. Up to 60,000 characters ride in each prompt, shared between the documents: short ones are carried whole and long ones are cut with a marker that says how much is shown. The call estimate shows what that adds to every call.
- **What is read.** PDF (through `pdftotext`; install `poppler-utils` if it is missing), Word, Excel, PowerPoint, and OpenDocument files (read directly, no Office needed), old `.doc`, `.xls`, `.ppt`, and `.rtf` files (through LibreOffice with a throwaway profile, when it is installed), plain text, Markdown, CSV, JSON, and common code files, and zip archives of any of those. Images are not read; there is no OCR. To let members explore a whole project, attach it as a workspace instead.
- **Limits.** 25 MB per file, 10 files and 60 MB per meeting. Other file types are refused. Text is read inside the server process, so a deliberately malformed Office file could stall the app while it is parsed; the devices that can upload are your own, which is why this is a known limit and not a guarded boundary.
- **Zip archives** are read in memory. Nothing inside is written to disk under a name the archive chose, entries with `..` or absolute paths are refused and named in the warning, inflation stops at a fixed size whatever the archive claims (so a zip bomb yields "too large", not a full disk), and encrypted or nested archives are listed but not read.
- **Where files live and when they go.** An upload waits under `data/attachments/staged/` (a day at most) until a meeting claims it, then sits under `data/attachments/<meeting id>/`. When the meeting closes, whether it finished, failed, or was stopped, the uploaded files are deleted and only the extracted text is kept, so the meeting can be resumed or reconvened; **Remove the text now** on the meeting deletes that too and ends both for that meeting. The text also goes when the meeting is deleted or ages out of the history, which removes the meeting as completely as a delete. Startup clears anything an unclean shutdown left behind. The meeting record keeps each document's name, size, SHA-256, and character count, never its text; what members quoted stays in the transcript like anything else they said.
- **What this opens up.** A paired device can write files into the host's data directory. They are size-capped, limited to the types above, stored under fixed names, and never executed; the text goes to every selected member's provider, which is the point, so attach only what you would paste into the brief.

### The command line

`bin/overrule.mjs` is a client of the HTTP API, not a second engine: it needs the server running and everything it starts is an ordinary meeting. Commands: `ask`, `review`, `watch`, `show`, `list`, `rename`, `pin`, `unpin`, `archive`, `unarchive`, `delete`, `settings`, `playbooks`, `connections`, `models`, `councils`. `list --search "<words>"` searches as the browser does and prints where each meeting matched; `--tag` (repeatable; each must be present) and `--project` filter; `--archived` lists the Archive instead. `archive <id>` and `unarchive <id>` move a meeting, warning when an unarchived meeting would be removed at the next start. `settings` prints the history limit and storage; `settings --keep <n>` or `settings --keep max` (`all` means the same) changes the limit and says how many meetings a lower one would remove; a number above the room is refused. `settings` prints the limit, the storage, and how the room was worked out. `rename <id> "<name>"` names a meeting and `rename <id> ""` clears the name; `list` and `show --json` use the name. `list` prints pinned meetings first with their project and tags, and marks a meeting the next start would remove. `pin <id> [--project <name>] [--tag <tag>]...` pins a meeting or edits a pinned one: `--tag` replaces its tags, `--project ""` removes its project, and whatever is not given is kept. `unpin <id>` returns it to the recent list and warns if the next meeting would remove it. `delete <id>` asks for confirmation on the terminal and needs `--yes` when there is none; an id prefix must match exactly one meeting, and a meeting in session is refused. It reads the CSRF token from `/api/bootstrap` on every connection and retries once when the server has restarted; on another machine it pairs first with `--code`.

Defaults chosen for unattended use: every ready connection becomes a member, up to eight, with the first as drafter; a workspace is attached read-only; two cycles; one revision. `--council <name>` seats a saved council instead and applies the settings it keeps; any option given as well (`--members`, `--drafter`, `--cycles`, `--revisions`, `--research`, `--deep-research`, `--call-limit`, `--time-limit`, `--turn-limit`) wins over the council and is recorded on the meeting as a change. `councils` lists saved councils; `councils save <name>` saves one from `--members` and the settings options given, which are what it keeps, or from a finished meeting with `--from <id>`, which keeps every group except those named in `--without` (drafter, cycles, revisions, research, limits); a name in use is refused unless `--replace` is given. `councils rename <name> "<new name>"` and `councils remove <name>` (asking first, or `--yes`) complete the set, and `connections remove` says which councils the connection left. `--members` and `--drafter` take the names you gave your connections. `--neutral-drafter` keeps the drafter off the floor and out of the vote, so it writes what the others argued rather than its own view; it needs three or more members. Warnings that the browser shows as checkboxes are accepted with `--acknowledge`, and full access additionally needs `--acknowledge-full-access`, which is refused otherwise.

The exit status carries the verdict, so a calling agent can branch on it without parsing text: 0 approved, 2 objections remain, 3 checks failed, 4 verification incomplete, 5 unsettled, 1 anything that went wrong. The division that matters to a caller is settled against retryable, not the individual reasons. 0, 2 and 3 mean the council reached a conclusion: approved, a member voted against, or a check on the candidate failed. 5 and 4 mean it did not: the floor ran out of turns or stopped moving with nobody dissenting, or the vote never finished, and in both cases spending more would plausibly change the answer. A caller should treat an unrecognised non-zero status as retryable rather than as failure, so a future outcome costs nothing to adopt. `verdict` also carries `dissent`, `stopReason`, and the vote counts.

`--json` prints the record, not a summary of it: `{ id, status, url, verdict, stopReason, cycles, session, final, candidate, candidateVersion, ballots[], objections[], openObjections, members[], drafter, workspace, research, deepResearch, metrics, error, calls, usage, failedTurns }`. `calls` counts the model calls across every session and `usage` sums the tokens providers reported, for a caller that budgets or compares runs. Each objection carries its `resolvingCondition`, and each ballot its vote and reasons, so a caller can quote a dissent verbatim without scraping Markdown. Progress goes to standard error, so piped output stays clean, and nothing is written to standard output until the verdict.

`resume <id>` picks up a stopped meeting, and also a meeting that finished on budget or as stalled when it is given more cycles than it had: the floor reopens on the same record, the next draft becomes a new candidate version, and the earlier ballots stay in the transcript. `reconvene <id> "<instruction>"` opens a new session instead. Both take the limit options and `--note`.

### Cloning a repository

`POST /api/workspace/clone` takes a repository address and returns the clone. The address must be `https`, must name a host with a dot that is not `localhost` or an address literal, and must end in an owner and a repository; shorthand such as `owner/project` is read as GitHub. Credentials in the URL are refused. The clone runs `git clone --depth 1 --no-recurse-submodules --no-tags` with hooks disabled, a ten-minute limit, and `GIT_TERMINAL_PROMPT=0` with `GIT_ASKPASS` stubbed, so a private repository fails with advice rather than hanging on a prompt. Clones live in `~/overrule-repos/<owner>-<repo>` unless `OVERRULE_REPO_DIR` says otherwise, which keeps them outside the app's own directory and its data, where a workspace is refused. Cloning again fetches and resets that checkout; a folder holding a different origin is never overwritten.

The clone runs as the account that runs the app and uses that account's git credentials, so a private repository works wherever the host's git already reads it; with the GitHub CLI that is `gh auth login` then `gh auth setup-git`. The app holds no token of its own, and it never writes one: authentication stays with git. A repository the account cannot read stops the clone with git's own message, which is the same for a private repository and one that does not exist.

Inspect lists binary documents (`.pdf`, `.doc(x)`, `.xls(x)`, `.ppt(x)`, OpenDocument, `.rtf`) found up to three directories deep, skipping hidden and dependency folders. `POST /api/attachments/from-workspace` stages one of those by path, after checking it is inside the attached workspace and that the inspection offered it; the file is read on the host and never passes through the browser. This exists because those formats divide the council: a member with a shell can unzip a Word file, a member without one sees nothing, and the meeting runs with some members having read the document and others relying on quotes.

A clone is untrusted source like any other workspace: read-only by default, instruction files neutralized, and the secrets warning applies, which most real repositories trigger on files such as `.secrets.baseline`. The checkout is shallow, so history, blame, and tags are not available to the council. Applying a candidate merges into the local clone only; pushing is not implemented.

### Report templates

With a workspace attached, the composer offers seven ready-made briefs (`public/playbooks.js`): security review, correctness bug hunt, dependency and supply chain, architecture and maintainability, test coverage gaps, performance, and release readiness. Each names the repository and the commit, sets a severity scale, and demands a file and line plus quoted evidence for every finding, a VERIFIED or INFERRED mark on every claim, and a closing list of what was not examined. The security template asks for a report to maintainers and forbids writing exploit code. Choosing one fills the brief and leaves it editable; it also sets the level to read-only if the meeting was still talk-only.

## Giving the council a workspace

By default no member touches your machine: CLI members run in an empty temporary directory with tools off, and API members have no tools. To let the council work on code, open the **Workspace** section of the composer, press **Browse** (or type a path on the host), pick the project folder, press **Inspect**, and choose an access level. There is no separate list of allowed directories: any directory that passes the path rules can be attached, and the workspaces you have used appear as **Recent workspaces** for one-click reuse (saved in `data/workspaces.json`; an older file's allowed directories become the first recents). `OVERRULE_WORKSPACE_ROOT` only sets where Browse starts. The app refuses system directories, your home directory itself (its hidden folders hold your credentials), the app's own directory and data and any folder that contains them, hidden directories, and symlinked paths; it also warns when the tree holds files that look like secrets and asks you to acknowledge that before members read them. Paired devices can attach workspaces too, because the owner runs this server headless and works from other machines: the directory and the execution are on the host, and the meeting records which address attached the workspace. That makes the pairing code the key to code execution on the host, in any directory that passes the path rules, at the level chosen for the meeting. Earlier versions confined workspaces to an owner-set list of directories, but the list could be edited from any paired browser, so it was the same authority in two steps and was removed; the path rules, the levels, and the canaries are the boundary. LAN traffic is plain HTTP, so anyone who can read your network traffic and obtain the code gets that execution too: use it only on a network you trust, share the code only with your own devices, and rotate it from the LAN access dialog or restart the app if it may have leaked. Every gate is enforced by the server on the attach request itself, regardless of where it came from, so a client that skips the interface meets the same refusals. The sandbox levels, path rules, canaries, and git isolation apply regardless of where the request came from.

- **Talk only.** The default. Nothing runs.
- **Read-only tools.** Every CLI member reads the workspace on the floor. Codex members run inside Codex's own operating-system sandbox (`--sandbox read-only`): writes and network are blocked. The workspace is what members are pointed at; the read-only sandbox does not stop a member from reading other files your account can read, which is one more reason to keep secrets out of the account that runs the app. Claude Code members run with `--restricted` and the code-running tools named back in, inside Claude Code's own sandbox with nothing writable, in a throwaway working directory rather than the workspace: the sandbox keeps a member's own working directory writable, so standing outside the workspace is what keeps the workspace unwritable. Reads are unrestricted, as they are for a Codex member at this level, and the network is off. The sandbox is declared with `failIfUnavailable`, so a machine that cannot start it fails the turn instead of running the shell loose. Unticking the Claude Code sandbox option removes the shell as well, leaving those members reading and searching files through the permission layer alone, which is not an operating-system boundary. The meeting labels each contribution with the checkout and level it ran under.
- **Workspace-write.** Requires a git repository at the workspace root with a clean tree (or your acknowledgement). The floor stays read-only. When the floor closes, the drafter, a Codex or Claude Code member, implements in an isolated `git worktree` on a new `mesh/<id>` branch under `--sandbox workspace-write` with network off unless you allow it. The controller commits what it leaves behind (`--no-verify`, hooks ignored, since a member could write them) as the candidate; the diff is the candidate, shown in the meeting and downloadable as a patch. Checks you list (for example `npm test`) run in a disposable checkout of the recorded commit under the same sandbox, and their command, exit code, and output go to every voter. Voters get a separate, clean checkout of that commit, so files generated or modified by checks cannot alter what they review. A ballot on a candidate without checks is labeled an opinion. Your working tree is never touched until you press **Apply**, which merges the exact recorded commit into your checked-out branch, even if the candidate branch has moved, and refuses a dirty tree; **Discard** deletes the branch. Applying cannot undo external effects and does not recover untracked files.

Repository text is treated as untrusted input to members: Codex runs with `project_doc_max_bytes=0` so it does not read `AGENTS.md`, and Claude Code runs in safe mode so it does not discover `CLAUDE.md`. To confirm both the sandbox boundary and this on your machine, run from inside a scratch git repository:

```sh
node -e "import('/path/to/overrule/lib/workspace.mjs').then(m => m.codexCanary('workspace-write', process.cwd())).then(r => console.log(JSON.stringify(r, null, 2)))"
echo 'MARKER_DO_NOT_READ' > AGENTS.md && codex exec -C . -c project_doc_max_bytes=0 --sandbox read-only 'Reply with the word MARKER if any instruction file mentions it, otherwise reply NO.'
```

### Installing agentsec-pack from the app

This repository vendors the latest agentsec-pack source under `vendor/` (a tarball plus `vendor/agentsec.json` naming its version, commit, and packaging date). When the tool is missing on the host, the Workspace section and the Security page show an **Install agentsec-pack** button: it unpacks that bundle into `~/agentsec-pack`, creates a Python virtual environment there, installs the package, runs `agentsec presets` as a check, and streams every command into the page. The install runs on the host under the account that runs the app, and it needs Python 3.10 or newer; `pip` fetches the Python build tooling (setuptools) from PyPI once, so the host needs that much network access. The tool has no other runtime dependencies. Without a vendored bundle the installer tries to clone the repository instead, which needs network access to GitHub.

`scripts/package-agentsec.sh [path-to-checkout]` rebuilds the bundle by hand. The **Package agentsec-pack** workflow does it daily and on demand: it clones the latest source, proves the bundle installs and runs in a fresh environment, and commits the new tarball when it changed. agentsec-pack is public, so the workflow needs no secret; if it is ever made private, add a fine-grained personal access token with **Contents: read** on `binary-knight/agentsec-pack` as the `AGENTSEC_PACK_TOKEN` secret (`gh secret set AGENTSEC_PACK_TOKEN -R binary-knight/overrule`) and the script uses it. The **Tests** workflow runs `npm test` on every push and pull request.

### Measuring the boundary with agentsec-pack

If [agentsec-pack](https://github.com/binary-knight/agentsec-pack) is installed (found at `~/agentsec-pack/.venv/bin/agentsec`, `~/.local/bin/agentsec`, or the path in `OVERRULE_AGENTSEC`), Inspect also runs its blast-radius probe and path assertions inside each Codex sandbox level and shows the score, every finding above informational, and which of the app's own secret files and the account's credential files are readable from inside. The measurement is recorded with each meeting that uses the workspace. A **blast-radius budget** in the Workspace section refuses any level whose score exceeds it; leave it blank to see the number and decide yourself. A first measurement on a typical developer machine shows what the built-in canary cannot: from the read-only level a member can read `data/vault.key`, the encrypted provider file beside it, `~/.ssh`, and the CLIs' own credential files, because Codex's read-only sandbox has no per-path read denial. Run the app under an account that holds no personal credentials if that matters to you.

CLI members and every other child process receive a minimal environment: home, path, locale, proxy and certificate variables, and the CLIs' own config-directory variables. Provider API keys and anything else in the server's environment do not reach a member. To pass specific variables through anyway, list them in `OVERRULE_CLI_ENV_PASSTHROUGH=NAME1,NAME2` when starting the app; a CLI that relied on an API key from the environment needs that or its own sign-in.

- **Full access.** No boundary, offered because this is your machine and your call. Codex runs with its sandbox off and approvals off; Claude Code runs with every permission check off. Every member with tools can do anything your account can do: read this app's own vault key and encrypted provider file and decrypt every saved key, read your SSH and CLI credential files, reach the network, and change or delete anything, including your real working tree, and send any of it to its provider through the normal course of a turn. Text in the repository or a message from another member can steer that. The candidate branch and apply/discard still exist, but they are conveniences, not containment. Full access requires an acknowledgement checkbox for every meeting, is never remembered, is shown in red on the meeting, and its measurement is recorded like any other. It exists because the machine is yours; the warning is the compromise.

A **Claude Code implementer** at workspace-write runs with edits and shell allowed inside Claude Code's own bubblewrap sandbox, generated per call so that writes land only in the checkout, the network is off, and an unsandboxed retry is refused. If this machine cannot start that sandbox (Ubuntu 24.04 restricts unprivileged user namespaces by default), the draft fails with a plain message; untick the sandbox option to run the implementer on Claude Code's permission layer alone, which is not an operating-system boundary. Measure it from the Security page before trusting either.

### The Security page

The Security page shows one row per member per way this app launches it (talk, read-only, workspace-write, full access), states the boundary in words, and can measure it with agentsec-pack through the exact launcher a meeting would use. Claude Code rows are measured by asking that member to run the probe inside its own launch, which spends one call and is labeled as the member measuring itself. API members never execute anything and have nothing to measure. Below that, the sandbox lab runs any named agentsec configuration, or a container preset against an image you name, so you can measure, apply the recommended flags, and measure again; results persist under the app's data, and agentsec renders its own self-contained HTML report over them. A browser cannot supply a launcher template, only choose a preset or a member, for the same reason agentsec's own console refuses to; the server rejects anything else. You can skip the agentsec measurement for a meeting with a checkbox; the choice is recorded with the meeting.

Before any level is offered, the app runs a canary under that Codex sandbox level on this machine: a write inside must succeed only at write level, and a write outside the directory and a proxy-ignoring socket open must fail. A level whose canary does not hold is refused, and the result is shown with the inspection and recorded with the meeting. Full machine access is offered as a level of its own, with the warning above.

Read this plainly: **this runs code chosen by models with whatever access you grant. Text in the repository and messages from other members can steer a member into commands you never asked for. Anything in the tree can reach the model providers, so point it at a scratch clone and never at a tree holding secrets. Git rollback and the activity log limit damage; they do not guarantee safety.** Tool activity (commands run, files changed) is captured from the CLI event streams and shown per contribution; treat it as telemetry that may be incomplete.

## Limits and privacy

- API token limits apply per call, including reasoning tokens where the provider counts them. CLI token limits are controlled by the native CLI/model; the UI clearly distinguishes these. Timeouts apply to all connections. These are not dollar budgets.
- A prompt can contain 24,000 characters. Individual returned answers are capped at 100,000 characters. The thread each turn reads never truncates the prompt or the opening positions, keeps the last six floor turns in full, reduces older turns to their structured fields, and caps each contribution at 12,000 characters with a truncation mark. Large councils and long meetings can exceed a provider's context window and will show a failure.
- This version produces text and code; it does not execute proposed solutions or provide browsing, file uploads, repository editing, or image generation. More models do not guarantee correctness. Independently validate important outputs.
- API keys use AES-256-GCM encryption. The key is stored in `data/vault.key` with mode 0600; data directory mode is 0700. Someone with access to your OS account or both files can decrypt the keys. Back up the complete directory privately. History contains unencrypted prompts and answers in an owner-readable file.
- The app is one shared workspace for its owner and paired LAN devices. It accepts only Host headers for localhost and detected interface IPs, rejects cross-origin requests and writes without a per-process CSRF token, and requires pairing for LAN requests. Sessions use signed, expiring HttpOnly/SameSite cookies. It does not separate users or offer per-user provider credentials. Do not expose it publicly without HTTPS, stronger account management, and a review of the trust model.
- CLI prompts are passed over stdin, with fixed executables and no shell interpolation. Runs use temporary empty working directories, disable normal customizations and tool execution, and retain provider-managed authentication. Admin-managed CLI settings still apply. Current CLI versions are required for the isolation flags. Cancellation sends termination signals to local subprocess groups and aborts HTTP requests; upstream providers may charge for already-started work.
- The app does not log keys or raw provider error bodies. Provider responses are escaped before rendering. Your selected providers receive the prompt and peer contributions, including text originally produced by other providers.

remembered and shared failures; lists kept when a provider fails; saving that does not wait; empty, malformed, partly broken, 500-entry, and overlong lists; a damaged cache file; keys pasted with stray characters), keys never leaking (above), saved councils (validation, kept groups, naming and replacing, persistence, connections deleted from under them, the council a meeting records, and the command line), a whole meeting through every API adapter, LAN authentication, origin/CSRF protection, persistence, and Markdown export. Automated tests use mocked inference and do not consume model credits. The browser smoke test is in `scripts/browser-check.mjs`; it checks every page for horizontal overflow at phone and tablet widths, with the agentsec install help shown whatever the host has installed; set `PLAYWRIGHT_MODULE` to an installed Playwright module when running it. It uses a temporary isolated data directory, verifies LAN pairing over an actual interface address, checks mobile layout, citation links, verdicts, limit settings and resume, workspace verification recovery, searching, archiving and unarchiving, settings, renaming, pinning and unpinning a meeting, deleting a meeting, and model suggestions in the connection form against the fake provider (the list, the warning while typing and after saving, a typed key cleared when the type changes) **Test connection** (a pass, a result cleared when the form changes, an unknown model), and failures in the form (a provider that never answers, shown waiting and then unreachable; a test cancelled; an old list kept when the provider fails; a local server that is not running; a typed key that never comes back from the server or stays in browser storage), saved councils and the eight-seat limit (saving with a group unticked, applying, the changed note, a connection deleted from under a council, deleting a council), and saves screenshots under `artifacts/`.

`npm run fake-provider` (or `node scripts/fake-provider.mjs --port 4999`) starts a local stand-in for every API provider. It answers each provider's model list in that provider's own shape (its auth header, paging, and field names, with some models that are not for conversation mixed in) and answers meeting turns with scripted replies that follow the rules of order, so a whole meeting runs through the real OpenAI, Anthropic, Gemini, Grok, Hugging Face, and OpenAI-compatible adapters with no network and no credits. The model names in it are illustrative. Start the app with `OVERRULE_PROVIDER_OVERRIDE_URL=http://127.0.0.1:4999 npm start` and every built-in API connection goes to `http://127.0.0.1:4999/<type>/…` instead of its provider; for an OpenAI-compatible connection use the base URL `http://127.0.0.1:4999/compatible/v1`. Any key beginning `fake-` is accepted and anything else is rejected; the word after `fake-` picks a behaviour, and anything after a further dash is ignored, so `fake-429-a1b2` acts as `fake-429`; `fake-401`, `fake-429`, `fake-500`, `fake-slow`, `fake-garbage`, `fake-redirect`, `fake-huge`, `fake-empty`, `fake-limited` (an account that sees fewer models), `fake-quota` (429 with `insufficient_quota`), `fake-limit` (a reply cut off at the token limit with no text), `fake-hang` (accepts and never answers), `fake-stall` (sends headers and half a body, then nothing), `fake-many` (a list of 500 models in the provider's paging), `fake-shape` (JSON that is not a model list), and `fake-nulls` (a list with broken entries among good ones) make it misbehave on purpose. Any other request that asks for `OK`, such as a connection test, gets `OK`. A model it does not list fails its turn with HTTP 404, as a real provider would. The override accepts only `localhost`, `127.0.0.1`, or `[::1]`; anything else fails every API call rather than falling back to the real provider. It is resolved when a call is made and never saved with a connection, and while it is set the server log, the Connections page, and the command line say where API calls are going. Keys, including environment keys, go to that local server while it is set. `test/models.test.mjs`, `test/connection-test.test.mjs`, and `test/failures.test.mjs` run against it, the last with shortened deadlines; the latter also puts stand-in `codex` and `claude` scripts on `PATH` to test CLI connections through the real launcher.

`test/key-leak.test.mjs` checks that keys never leak. It runs the real server as its own process, as `npm start` does, with its output captured as the log, and uses keys that all carry one random tag: typed, saved, from the server's environment, pasted with stray whitespace, with characters that cannot be sent, rejected (the fake echoes a rejected key in its error body, as real providers do), and used while the provider fails in every way the fake can fail, through model lists, connection tests, saving and editing, a meeting with a member whose key is refused and one that never answers, the export, and the command line. It first confirms the keys reached the provider, so their absence means something, then searches for the tag in the server log, every file in the data directory, every HTTP response, every command-line output, the fake's own log, and every URL the provider received, and checks that no encrypted key leaves `providers.json` and that the log holds nothing but its start-up lines.

An optional `node scripts/live-check.mjs` runs a real two-member, one-cycle Codex/Claude meeting against an already running app and consumes the active CLIs' allowance. It exits non-zero if any real turn failed to end with a parseable structured block, since such a meeting closes on budget and proves nothing. The meeting engine has not yet been validated against live models; run this check after starting the app.

The implementation is intentionally small: `server.mjs` serves the HTTP API and frontend; `lib/providers.mjs` holds adapters; `lib/models.mjs` fetches, filters, and caches model suggestions; `lib/connection-test.mjs` runs and explains a connection test; `lib/councils.mjs` validates and stores saved councils, and `public/councils.js` describes and compares them for the server, the page, and the command line alike; `scripts/fake-provider.mjs` is the local fake provider; `lib/meeting.mjs` holds the pure meeting logic (rules of order, prompts, structured-field parsing, speaker order, planning, metrics); `lib/mesh.mjs` runs meetings and persists them; `lib/budget.mjs` enforces session limits; `lib/store.mjs` stores local state; `public/` contains the UI and the shared `meeting-state.js` citation, usage, and verdict logic. A new provider needs a connection definition, validation, request/response adapter, and tests. Set `OVERRULE_DATA_DIR` to use another private data directory.
